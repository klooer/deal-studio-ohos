1. 分层

prompt ──► agent route ──► Vera source ──► compiler ──► VM ──► ArkUI (VeraPreview)
              (VeraBuildRoute)    (.vera)   (VeraCompiler)        (renderer)
层是什么位置
Vera路由发出、模型书写的 DSL——ui.* 目录调用、state、处理器、intent.call、sdk.calldocs/examples/shanghai-layover.vera
VeraCompiler带恢复地解析 Vera、做类型检查，再输出 VM 程序；compileVeraSource 抛出携带 .diagnostics 的 CompileError（而非把诊断返回出来）vera/VeraCompiler.ets
VM运行编译后的程序；intent 式目标会得到真实派发vera/VeraCompiler.ets（运行时）、vera/VeraVm.ets
VeraPreview把运行中的程序渲染成原生 ArkUI；自己保留一份硬编码的节点种类清单，启动时若与目录不一致就报警components/VeraPreview.ets
ArkTS应用本身用的宿主语言——编译器、VM、渲染器、目录都靠它写。模型和 composer 从不写 ArkTS，只写 Vera—

目录是一份纯数据描述（vera/VeraUiCatalog.ets）。编译器接口、校验器和模型提示词都从它生成，所以彼此不会漂移；唯独渲染器另留一份清单，并在启动时校验一致性。新增一个组件只需编辑目录、在 VeraUi.ets 加一个 case、在 VeraPreview.ets 加一个分支——编译器、校验器和提示词会自动跟着目录走。

2. 目录：section 与 part

界面由若干 block 拼装而成，它们都遵循同一种格式 FragmentSpec（vera/VeraTemplates.ets）：状态字段、处理器、一个视图骨架（sections.push(ui.Section(...))），加上 content/port/hole 的占位 token。block 分两类：

  • Section：目录自带的预制模板。在 fragments()（VeraTemplates.ets:2422）里注册了 29 个：checklist、record_log、master_list、search_list、detail_view、list_summary、filter_box、bar_chart、series_chart、trend_chart、number_strip、breakdown_table、data_table、metrics、timer、timeline、itinerary、progress_goal、progress_line、key_facts、live_facts、spotlight、note、rating、actions、intent_panel、calendar_event、reminders、settle_up。Jev 只在其中一个子集里挑，对应 section 能整体搞定的那些需求：READY_KINDS（10 个）给 ready 需求，LIST_SECTIONS（record_log, reminders）给列表，timer 给倒计时。
  • Part：composer 自己的 block（clock、list、输入/控件、计算值/公式、effect）。它们由 part(kind, fields, functions, view) 按 Jev 的逐属性选择用代码拼装而成，并非取自模板。compositionParts(comp) 负责收集它们。

composer 通过 assembleProgram(comp)（vera/VeraCompose.ets:3763）把 section 和 part 缝合成一个程序，输出 Vera 源码。快路径上的代码由 composer 生成；模型不写任何整程序 Vera。 模型只负责填充 section 的文本/content（以及 section 内部的小型 目录 hole——某个函数体），外加 §5 介绍的 hole。

2.1 一个 part 是怎么拼出来的

part 是用代码拼出来的，不是往模板里填的。part()（VeraCompose.ets:2895）是个小工厂，把四个数组打包成一个 FragmentSpec：

function part(kind: string, fields: Field[], functions: string[], view: string[],
             supportClass: string = '', initStatements: string = ''): FragmentSpec {
  // fields → 状态字段 + 初始值；functions → 处理器函数体；view → 视图行
  let state: StateFieldSpec[] = []
  let inits: string[] = []
  for (let f of fields) { state.push(new StateFieldSpec(f.name, f.type)); inits.push(f.name + ': ' + f.init) }
  let spec = new FragmentSpec(kind, '', supportClass, state, initStatements,
                              inits.join(', '), functions.join('\n\n'), view.join('\n'), [], [])
  spec.indexed = false   // 是 part，不是目录 section
  return spec
}

这四个入参正好对应 FragmentSpec 里的四块：fields → 状态、functions → 处理器、view → 视图行、kind → part 的名字。这里没有套模板这一说——这些数组都是照着 sketch 和 Jev 的回答，在代码里一行行攒出来的。

下面这组 builder，每个各管 Composition 的一块，各自产出一个 part：

  • figuresPart（:3110）——其余 part 都要引用的那批 let 局部变量（每个输入、时钟的时间、列表的条数和总和、每个值的公式），外加让目录 section 能经端口读到某个值的 port 函数。
  • inputsPart（:3170）——每个输入配一个控件和一个 setter；用哪个控件由 Jev 决定（comp.widgets.get(input.id)），进而决定走哪条 ui.* 调用（ui.Select、ui.Slider、ui.Toggle、ui.TextField……）。
  • clockPart（:3065）、listPart（:3239）、effectsPart（:3485）——分别是时钟的 Ticker 和 start/stop/reset、列表的 LogEntry 类与增删处理器、界面按钮和手机应答横幅。
  • heroPart（:3145）、summaryPart（:3227）——只管布局，不带状态也不带处理器（part('hero', [], [], view)）。
  • widgetPart（:3489）——chat widget 的两段式骨架。

compositionParts(comp)（:3495）按界面顺序把它们收拢起来，然后特意多做了一步：把每个 part 的 viewBlock 清空，把里面的视图行缝进末尾那个 screen part：

let view: string[] = ['{']
for (let p of parts) {
  for (let line of p.viewBlock.split('\n')) { if (line.length > 0) { view.push('  ' + line) } }
  p.viewBlock = ''
}
view.push('}')
parts.push(part('screen', [], [], view))

figures part 会定义一批局部变量（let duration = …; let tip = …;），hero、summary、list 这些 part 的视图行都要引用它们，所以它们必须落在同一个作用域里。把所有视图行折进一个 { … } 块，既保住了这些变量的作用域，又不会和同屏的其它目录 section 混在一起。

之后 assembleProgram(comp)（:3763）把这些 part 连同 Jev 选定的目录 section（comp.blocks）一起拼成 Vera 源码：

export function assembleProgram(comp: Composition, blockValues: Map<string, string>[] = [],
                               custom: FragmentSpec | null = null): string {
  if (comp.unbound.length > 0) { return '' }   // 有开放槽位 → 不出程序
  return assemblePlan(screenPlan(comp, blockValues, custom), true)
}

开头那个守卫就是“带开放槽位的计划不予交付”那条规则：只要有还没绑定的值，拼装就到此为止。screenPlan 把 part 和 section 交错排好，assemblePlan 输出状态块、处理器和合并后的视图。

所以说，快路径上的代码是 composer 写的——Jev 只决定了每个槽位里放哪个控件、公式、effect 和触发时机；剩下的交给 builder，一个字段、一个处理器、一条 ui.* 调用，把字符串一点点攒出来。

3. Jev

Jev 是 TypeSafe 的 System One 模型（jev-latest，https://api.typesafe.ai/v1/systemone），调用时携带 Bearer key——即 TypeSafe key，由 --ps typesafeKey ... 启动参数传入，并以 selectorKey 持久化到 {filesDir}/vera/settings.json（vera/SettingsStore.ets、EntryAbility.extractSelectorKey）。

所有线上 Jev 调用都走两个入口之一：askJev（vera/VeraCompose.ets:3909），在 agent/AgentAppHost.ets:21 接为 host.askJev；以及 selectEdit（vera/VeraComposition.ets:446），仅用于 refine 路径。Jev 的职责可以概括为一句话：逐项提问，以概率/置信度作答。具体落在六处：

  1. 组合选择。composeNeeds（vera/NeedsChoose.ets）里发起两次 Jev 调用：先是 section-or-part 调用（buildChooseRequest），对每一个 section 和 part 都能胜任的需求，把两者并排摆出来让 Jev 选（倒计时 → timer section 或 clock part；列表 → 一个 LIST_SECTIONS section 或 list part；每个 ready 需求 → 一个 READY_KINDS section，或人自己的记录）；接着是 逐属性 调用（VeraCompose.ets 的 buildComposeRequest），处理剩下的部分——每个输入配一个控件、每个值配一个公式、每个事件配一个 effect 和一个触发时机，再加主题，以及某个 section 是否需要真实数据。
  2. 问题（agent/AgentQuestions.ets，askBlocking）。厘清 sketch 中的问题，只保留那些默认值兜不住的。
  3. 剩余对齐（agent/AgentAlign.ets，alignLeftovers）。先把 agent 的 section 留下的开放项跟目录对齐，避免把 section 已经覆盖的细节再写一遍。
  4. 槽位值（VeraSectionCompose.ets 的 buildSlotRequest，经 VeraAgent.ets:196 的 host.askJev）。读取各 block 槽位的取值。
  5. 校验（agent/AgentClaims.ets、agent/AgentHole.ets）。Jev 拿模型写的代码逐条对照每个需求：哪些声明的需求程序还没做到（claimsUndone）、哪些开放槽位界面已经覆盖（claimsDone），以及 hole 自己的 verify。
  6. Refine（vera/VeraComposition.ets，selectEdit）。当编辑已有组合而非从零重建时用到。

Jev 从不写文本或代码，它只在目录或 composer 已备好的选项里做选择。这条准则借自 json-render 的 Jev composer，这里把它推广到带逻辑的程序：Jev 回答一个个独立问题，composer 用代码拼装结果，程序跑起来之前什么都不计算。

Jev 不负责查找 intent 或 SDK 函数。 一个请求需要哪些手机 intent 与 SDK 函数，靠的是 embedding 而非 Jev：findIntentFunction（关键词与 embedding 排序并用）和 findSdkFunction（先 embedding、后关键词缓存）在 hole 路径中按手机槽位逐个跑（vera/VeraIntentIndex.ets、vera/VeraSdkIndex.ets，外加 *EmbeddingCache 模块）。UI 目录本身也由 selectUiForPrompt（embedding）为提示词收窄，跟 Jev 无关。早期用于 Jev intent 预筛选的 vera/JevSelector.ets（selectDomains/selectTargets）和 block section 选择的 vera/VeraSectionCompose.ets（selectSections），已随 block 管线移除而废弃，在当前代码树里再无调用方——代码还留着，但不在线上路径上。

4. 需求计划

两条路径最终都产出一个 ScreenPlan（vera/ScreenPlan.ets）：界面的 state（具名值）、它的 slots（每一件它要做的事，读什么、写什么、是不是手机动作），以及填充它们的 components。组件的 fill 取下列之一：FILL_OPEN、FILL_PART、FILL_BLOCK、FILL_EFFECT、FILL_HOLE、FILL_REPORTED。槽位在被某物填充之前一直是 open 状态；只要还有开放槽位，计划就不会交付。

计划始于一个 sketch——生成模型在关闭 thinking 时写出的 JSON：输入、常量、带公式的值、一个倒计时或 stopwatch、一个列表、事件（手机做什么、何时做）、ready 需求、其它条目，再加至多两个问题。模型收到 NEEDS_PROMPT（vera/NeedsPlan.ets:64）的提示，回复由 parseSketch（vera/VeraCompose.ets:225）解析。sketch 是模型的活，与 Jev 无关。它会反复请求直到拿到一个：先试一次，再带着错误引用重试一次，最后开启 thinking 再试一次。

sketch 是两条路径之间的枢纽：两条路径都要画它，而快路径拼不出程序时，慢路径正是对照它来书写的。

5. 两条路径

路由（agent/VeraBuildRoute.ets，buildScreen）是生成新界面的唯一入口，Generate 界面和 chat 都从这里走。它只决定由哪个 builder 交付，自己从不从零生成，调用方也不行。

5.1 快路径——有 Jev

runAgent（agent/VeraAgent.ets）→ composeNeeds（vera/NeedsChoose.ets）：

  1. 计划。 模型写出 sketch（thinking 关闭，按上面的方式重试）。
  2. 问题。 sketch 的问题在卡片上展示给人；只要给了非默认回答，就重新规划。
  3. Jev 调用 #1——section 还是 part。 对 sketch 做一次 Jev 调用。凡是 section 兜不住的选项，都在询问 之前 就依据计划自身的事实移除，所以一个选择不会被收回。Jev 没给选择的，就保留 part。
  4. Jev 调用 #2——逐属性。 一次 Jev 调用搞定控件、公式、effect 和触发时机，不再重问 #1 已定的事。若不回答就再问一次。
  5. 拼装。 readComposition → Composition → assembleProgram 从挑好的 section + part 输出 Vera 源码。
  6. 填充。 书写 section 的文本/content（必须真实时来自网络搜索），并填充其小型目录 hole（vera/SectionFill.ets、SectionFillApp.ets）。
  7. 检查。 拼好的程序编译一次，并逐个触发处理器运行；失败则把错误以 SEARCH/REPLACE 编辑的形式回传修复，至多两次（agent/AgentRepair.ets、settleProgram）。

若 composer 产出程序，result.vbc2 非空，路由返回 OUTCOME_AGENT。这条路径上不出现模型写的整程序代码——代码由 composer 生成，模型只填了文本和小 hole。

5.2 慢路径——没有 Jev，或快路径交付不了时

当 composer 拿不出程序（Jev 没回答，或 sketch 留下了现成物填不上的槽位），路由就落到 writeWholeScreen（VeraBuildRoute.ets:59）：

  1. 模型把整个界面当成一个 hole 来写——即 Vera 源码，对照计划已画好的 sketch（没有 sketch 时则对照裸请求）。writeHole（agent/AgentHole.ets）是书写者；它对照 Generate 页加载好的 Vera 技能（rawfile/vera-skill.txt，{{UI_CATALOG}} 已拼入）来写，这份技能以 host.language 传入宿主——AgentHole 用 host.language.length === 0 作门控（没有技能就没有 hole）。
  2. 对每个 手机槽位，应用自己的查找会先跑一遍——findIntentFunction（关键词与 embedding 排序并用）和 findSdkFunction（先 embedding、后关键词缓存）——section 只能调用它们返回的目标。每个 sdk.call 目标在交付前都要过一遍检查。
  3. 写好的 section 编译一次，并逐个触发处理器运行；失败则把错误以编辑形式回传修复，至多两次；快速尝试之后，再开启 thinking 多试一次。
  4. Jev 拿它对照每个需求（claimsUndone/claimsDone）；被判为没做到的需求会被重新请求。若仍不行，就把能跑且做到了一部分的最佳尝试连同缺什么一起交付；一个都跑不通，就在原位放一条说明；<cannot>（本手机无物可做）则按书写者所说上报、不重试。

若整屏 hole 能交付，路由返回 OUTCOME_AGENT（界面建好了，只是这次全靠模型单独完成）。若它也失败，路由返回 OUTCOME_NOT_BUILT 并附上原因——路由除了它不从零生成，调用方也一样；chat 和 Generate 界面都会显示这个原因。

慢路径要求 request.mode === 'deepseek'（云），并且整屏 hole 是开启的（默认即开）。在 MODE_LOCAL（端侧 Qwen）或 MODE_SERVER 下没有整屏兜底，所以无 Jev 时这些模式直接返回 OUTCOME_NOT_BUILT。

6. 优雅降级——没有 Jev 时会发生什么

一个答不上来的 selector，绝不能卡住整个生成。 这是每个线上 Jev 调用点都恪守的准则，也是无 Jev 时走的是慢路径而非直接失败的根本原因。

Jev 角色无 key / 不可达对管线的影响
组合选择（NeedsChoose、VeraCompose）askJev 返回 ''（空 bearer 时 401，或捕获到异常）；重试一次；composeFromSketch 返回 'Jev did not answer twice' 且拿不到组合composer 拿不到结果 → 路由落到 writeWholeScreen
问题 / 对齐 / 槽位值（AgentQuestions、AgentAlign、VeraSectionCompose）空回答 → 保留默认值、不做对齐、不读槽位值照常推进；以计划自身的默认值为准
校验（AgentClaims、AgentHole）空回答 → claimsUndone/claimsDone 返回 []（文档注明："[] when Jev did not answer"）没有未满足的声明，也就无可修——写好的界面照原样交付
refine（VeraComposition.selectEdit）空回答 → 编辑不生效既有组合原样保留

askJev（vera/VeraCompose.ets:3909）从不抛异常：返回非 200 或捕获到异常时，一律 noteService(SERVICE_JEV, false, ...) 并 return ''。线上各调用方都能像上面那样容忍空串。（JevSelector.ets 的 selectDomains/selectTargets 和 VeraSectionCompose.ets 的 selectSections 同样是宽失败，但它们没有调用方——见 §3。）

净效果：没有 Jev，界面照样能建出来——靠模型写整屏 hole（慢路径，约 30 秒起步，也就是 Jev 出现之前的生成成本）。有 Jev 时，快路径从挑好的 section/part 拼装，中位耗时约 2-7 秒（docs/agent.md 结果：纯 composer-part 为 2.0 秒，带书写 section 时达 6.7 秒）。这次 23 个提交的 dev/main 合并让 Jev 在快路径里更吃重（需求计划的 section/part 选择），但并未给慢路径新增 Jev 依赖：整屏 hole 的 Jev 校验在合并之前就已经在，并且早已能容忍 Jev 缺席。

查找 intent 与 SDK 函数这件事完全不靠 Jev：它走的是 embedding（findIntentFunction、findSdkFunction），当 embedding 模型不在（没有 llama.cpp 的 stub 构建）时回退到关键词。所以哪怕是 stub 构建，手机函数照样找得到——只是按关键词匹配排序，而不是按语义。

7. 开关与启动参数

所有启动参数都持久化（{filesDir}/vera/settings.json）并在重启后保留；没有一个写进源码。

参数作用
--ps cloudKey sk-...云模型的 API key（provider 中性别名；deepseekKey 是历史名）
--ps apiBase URLchat-completions 基址；引擎会追加 /chat/completions
--ps apiModel NAME请求里发送的模型名
--ps typesafeKey KEY启用 Jev。 缺它时每次 Jev 调用都按 §6 回退
--ps reasoningEffort low|high|max生成前模型推理的力度
--ps exaKey KEYchat 的网络搜索 key（可选；缺它则没有搜索工具）
--ps veraServer URLvera-server 地址，用于 Server 生成模式
--ps veraTemplateSelect 0为本会话禁用 Jev 模板路径（用来与纯生成对比）
--ps veraOrder blocks-first在 agent 之前先跑 blocks
--ps veraCustom 0关闭书写式（模型）section
--ps veraWhole 0关闭整屏 hole——不要和无 Jev 并用，否则啥也交付不了

apiBase/apiModel 可以指向任何 OpenAI 兼容的 chat-completions 端点；DeepSeek 原生字段（thinking、reasoning_effort）只在 settings.isDeepSeek() 为真（基址是 DeepSeek，或模型名里含 deepseek）时才发送，所以把 apiBase 指到别处会自动把这套方言关掉。Jev 不管云 provider 是谁，始终调用 api.typesafe.ai。

8. 可观测性

  • 阶段（vera/RunStages.ets）：每一步都标明是谁做的——WHO_MODEL、WHO_PHONE、WHO_JEV——以及墙钟耗时。Generate 界面的 metrics 标签页通过 attemptsPanel()、tokensPanel()、toolsPanel()、servicesPanel()（pages/GeneratePage.ets）把它们画出来。
  • 服务健康（vera/ServiceHealth.ets）：noteService(SERVICE_DEEPSEEK, ok, ...)、noteService(SERVICE_JEV, ok, ...) 每次调用都 ping 一下；services 面板显示可达性。
  • 工具日志（vera/ToolLog.ets）：toolCount/toolSpanSince 把手机查找的耗时计入模型阶段。
  • 追踪：每个写出的 hole 都会被记录——应用追踪里的一个 hole 事件，以及每次宿主运行旁的 holes.jsonl；tools/vera-harness/hole-report.py 按反复出现的需求归并（也就是目录里缺的那些 block）。

10. 核心思想（每条一行）

  • Jev 挑选，composer 拼装，模型只写 hole。 Jev 从不写文本或代码，只就现成选项回答一个个独立问题。
  • 统一 block 格式（FragmentSpec）目录 section 和 composer part 共用，拼装器一视同仁。
  • 目录是纯数据。 编译器、校验器和提示词都从它生成；唯独渲染器另留一份清单，并在启动时做漂移检查。
  • 规划和构建都各有快慢两条路。 Jev 挑现成的（快），模型写那些没有现成物可做的（慢），一路退到把整屏当成一个 hole。
  • sketch 是枢纽。 两条路径都要画它，快路径拼不出时，慢路径正是对照它来写。
  • 答不上来的 selector 不得卡住生成。 每个 Jev 调用点都有退路——退到整个目录、退到 part、退到 []——所以无 Jev 只是慢路径，不是失败。
  • intent 查找靠 embedding，不靠 Jev。 findIntentFunction/findSdkFunction 按语义给手机函数排序（stub 构建回退到关键词），所以没有 Jev 也能找到手机函数——Jev 干的是在现成选项里挑选，不是找手机函数。
  • 路由除了它不从零生成，调用方也一样。 整屏 hole 是最后的模型手写退路；再不行，就是 OUTCOME_NOT_BUILT 并附上原因。
  • 还有开放槽位的计划不予交付。 计划要求界面做的每一件事都必须被填上——用 section、part、手写 hole 或一条说明。
